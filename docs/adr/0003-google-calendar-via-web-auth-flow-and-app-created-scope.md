# Google Calendar via launchWebAuthFlow and the calendar.app.created scope

The extension writes only to a Shift Calendar it creates, using the `calendar.app.created` scope, so it can never read or delete events in the user's other calendars and Sync may freely delete anything it finds there. Read-only `calendar.calendarlist.readonly` access recovers the existing Shift Calendar when its local ID is lost. It authorizes with `chrome.identity.launchWebAuthFlow` and silent `prompt=none` renewal instead of `getAuthToken`, because the tool targets any Tenant's employees and `getAuthToken` works only in Google Chrome, not other Chromium browsers. No refresh token or client secret is stored. The non-sensitive `userinfo.email` scope identifies the connected Google account in setup and supplies a login hint for renewal. Explicit connection shows the account chooser; renewal rejects a different account. Signing out clears the token, email, calendar ID, and Sync history while retaining the ADP Position and time zone.

## Consequences

Google Auth Platform classifies `calendar.app.created` and `calendar.calendarlist.readonly` as non-sensitive (calendar-list scope added and confirmed in the project's Data Access page on 2026-10-09). Public distribution requires publishing the OAuth app to Production. Existing users need to authorize the added scope via Connect Google; a token without list access must fail lookup rather than create a duplicate calendar.

The extension reads the remembered ID with `calendars.get`. When absent or deleted, it searches all calendar-list pages, including hidden owned calendars, for the Shift Calendar name and managed description. If previous versions created duplicates, it picks the lowest ID deterministically and preserves the others' history. Before adopting a discovered calendar, `calendars.get` verifies access under `calendar.app.created`; calendar-list access alone cannot authorize event reconciliation. Lookup errors stop Sync. Only a successful search without a match allows creation.

Calendar lookup followed by creation is not atomic across separate browser installations. The background queue serializes creation within one extension instance; simultaneous first Syncs on separate devices can still race. Renaming or changing the managed description prevents recovery after local ID loss.
